# expassign — библиотека назначения экспериментов на запросы

Библиотека на C++20 без внешних зависимостей: по описанию запроса (набор
свойств + идентификаторы пользователя) определяет, в какие эксперименты и в
какие группы этих экспериментов попадает запрос.

## Модель

**Свойства запроса** (`Request`):

| Тип      | Пример                          |
|----------|---------------------------------|
| строка   | `service = "web"`               |
| булево   | `internal = true`               |
| версия   | `app_version = 1.2.3.4` (компонентов может быть сколько угодно; `1.2 == 1.2.0`) |
| домен    | `host = "www.example.ru"`       |
| регион   | `geo = 213` (целочисленный id) либо определяется по `Request::ip` |

**Ограничения** (по одному классу на тип свойства, `include/expassign/constraints/`):

* `StringConstraint` — значение входит в набор строк либо, наоборот, не входит;
* `BoolConstraint` — точное значение true/false;
* `VersionConstraint` — набор интервалов с включающими/исключающими границами,
  текстовый формат `"[1.0,2.0); (3.1.4,]"` (пустая граница — бесконечность);
* `DomainConstraint` — шаблоны вида `*.example.{tld}`: `*` слева — любое число
  дополнительных поддоменов (включая ноль), `{tld}` справа — любой один домен
  верхнего уровня;
* `RegionConstraint` — набор регионов, в один из которых регион запроса должен
  входить (или не входить). Вхождение проверяется по дереву регионов
  (`RegionTree`): у каждого региона, кроме корневого, есть родитель, регион
  входит в заданный, если совпадает с ним или лежит внутри по цепочке предков.
  Регион запроса берётся из явного id (`Request::regions`), а если его нет —
  определяется по `Request::ip` через диапазоны IP того же дерева
  (IPv4 и IPv6).

Отсутствующее в запросе свойство не удовлетворяет никакому ограничению на него
(для региона «отсутствует» — значит регион не удалось определить ни по id, ни
по IP).

Ограничения эксперимента — OR-список AND-групп («вариантов»): эксперимент
подходит, если полностью выполнен хотя бы один вариант. Пустой список —
без ограничений.

**Разбиение пользователей.** У эксперимента заданы тип идентификатора
(`id_key`), алгоритм хеширования, соль и группы (testid'ы), занимающие
диапазоны бакетов (возможно, с дырами): `hash(ids[id_key] + salt) %
total_buckets` выбирает бакет, бакет — группу; бакет вне всех групп — нет
назначения (holdout). У группы могут быть секции с полезной нагрузкой
(`params`) и собственными ограничениями — для выигравшей группы возвращаются
индексы подошедших секций.

Хеш-функции подключаются через `HasherRegistry`: каждое разбиение указывает
алгоритм (в конфиге — префикс соли до `:`, например `XXH3:abcd`). В комплекте
самодостаточный `XXH64` (проверен на эталонных векторах), зарегистрированный
по умолчанию и под `""`, и под `"XXH3"` — **это подстановка**: для
совместимости разбиений с продакшеном зарегистрируйте настоящий XXH3 (обёртку
над `xxhash.h`).

**Измерения** (`DimensionConfig`) — «эксперименты более высокого порядка»:
собственные ограничения, соль и слоты. `hash(id + dim_salt) % total_slots`
даёт слот; запрос попадает только в тот эксперимент, которому принадлежит
слот. Слоты экспериментов одного измерения не пересекаются (это валидируется),
поэтому внутри измерения эксперименты взаимоисключающи, а эксперименты разных
измерений пересекаются свободно — так управляется совместимость экспериментов.
В общем случае у эксперимента цепочка таких проверок (`SlotCheck`) — вложенные
разбиения.

**Уплощение** (`Flatten`): ограничения и параметры разбиения измерения
переносятся внутрь каждого его эксперимента; матчеры работают с плоским
списком `FlatExperiment`.

## Загрузка конфига

`LoadExperimentsJson` читает продакшен-формат — массив записей вида
`{restrictions, places, testids, type}`:

```json
{
  "restrictions": [{"services": "serv1, serv1-mobile",
                    "regions": "115",
                    "browser__app_versions": "[2025.12.3;+inf)"}],
  "places": [
    {"salt": "XXH3:12cb387f...", "id": 64, "size": 100,
     "slots": "0, 1, 2, ..., 14", "slots_count": 15, "percent": 15.0},
    {"salt": "XXH3:3242530d...", "id": 64, "size": 3}
  ],
  "testids": [
    {"slot": 0, "testid": "1467025", "percent": 5.0,
     "sections": [{"params": "some data"}]}
  ],
  "type": "ABT"
}
```

Отображение на модель:

* `restrictions` — массив блоков: OR между блоками, AND между ключами блока.
  Тип ограничения определяется `ConfigSchema`: по умолчанию `regions` —
  региональное, ключи `*_versions` — версионные (формат `[2025.12.3;+inf)`:
  границы через `;`, `+inf`/`-inf`/пусто — бесконечность), остальные —
  строковые наборы через запятую; схему можно дополнить (bool, домены).
* `places` — цепочка разбиений: все места, кроме последнего, требуют `slots`
  и становятся проверками слотов; записи, разделяющие одинаковую тройку
  (id, соль, size), образуют общее измерение — их слоты валидируются на
  пересечение между записями. Последнее место задаёт разбиение на группы.
* `salt` вида `XXH3:abcd` — алгоритм и соль; `id: 64` — тип идентификатора,
  значение берётся из `Request::ids["64"]`.
* `testids` — группы: `slot` — бакет последнего места; `sections` с `params`
  и необязательными собственными `restrictions` попадают в
  `GroupRange::sections`, подошедшие секции возвращаются в `Assignment`.
* `percent` и `slots_count` — информационные (slots_count сверяется со
  списком слотов).

## Возможные подходы к матчингу

1. **Наивный перебор** — для каждого эксперимента проверить все его
   ограничения. O(N·C) на запрос, тысячи экспериментов дают миллисекунды.
   Зато тривиально корректен — используется как эталон в тестах
   (`NaiveMatcher`).

2. **Инвертированные индексы + битовые множества** *(реализован,
   `IndexedMatcher`)*. Наблюдение: свойств мало (десятки), а экспериментов
   много (десятки тысяч), и почти всю работу можно вынести в построение
   индекса. Для каждого свойства строится структура, которая за O(1)–O(log K)
   отдаёт битсет экспериментов, чьё ограничение на это свойство выполнено
   (эксперименты без ограничения в битсете всегда взведены):
   * строки — hash-map «значение → список экспериментов» (отдельно позитивные
     и негативные наборы);
   * булевы — три предвычисленных битсета;
   * версии — все границы интервалов режут ось версий на элементарные регионы,
     на каждый регион предвычислен битсет; запрос — бинарный поиск региона;
   * домены — префиксное дерево по меткам хоста от TLD к младшим со
     специальным ребром `{tld}` и пометками `*` в узлах;
   * регионы — hash-map «регион → эксперименты»; на запрос регион
     разрешается один раз (id или IP), затем hash-map проверяется для
     каждого предка по цепочке дерева регионов (глубина — единицы).

   Ответ на запрос — И (AND) битсетов по всем свойствам (это линейные проходы
   по N/64 машинных слов с ранним выходом), затем для выживших кандидатов —
   проверка слота и выбор группы; хеши кешируются по паре (идентификатор,
   соль), так что эксперименты одного измерения считают хеш один раз.
   Несколько ограничений одного эксперимента на одно свойство (своё +
   унаследованное от измерения) раскладываются по «слоям» свойства, слои
   пересекаются как независимые свойства.

3. **Дерево решений / interval tree по самым селективным свойствам** —
   рекурсивно делить эксперименты по значениям свойств. Даёт хорошие
   результаты при сильно селективных конфигурациях, но плохо переносит
   отрицания, «дырявые» ограничения (эксперимент без ограничения на свойство
   должен попасть во все ветки — дублирование) и требует балансировки.

4. **Компиляция условий** (JIT/кодогенерация в один большой switch) — минимум
   накладных расходов на запрос, но сложность инфраструктуры несоизмерима с
   выигрышем против варианта 2.

Выбран вариант 2: он равномерно быстрый на любых конфигурациях, не деградирует
от отрицаний и отсутствующих ограничений, прост в проверке на эквивалентность
наивному и укладывается в бюджет «десятки тысяч экспериментов за < 1 мс» с
запасом на порядок.

## Замеры

Release-сборка, случайные конфигурации (2–5 ограничений на эксперимент, все
пять типов), см. `bench/bench.cpp`:

| Экспериментов | IndexedMatcher, avg | p99      | NaiveMatcher, avg |
|---------------|---------------------|----------|-------------------|
| 1 000         | 10 мкс              | 34 мкс   | 200 мкс           |
| 10 000        | 48 мкс              | 104 мкс  | 1.81 мс           |
| 20 000        | 108 мкс             | 164 мкс  | 4.94 мс           |
| 30 000        | 160 мкс             | 222 мкс  | 7.60 мс           |

Построение индекса на 30 000 экспериментов — ~1.4 с (делается один раз на
обновление конфигурации, на путь запроса не влияет).

## Сборка и тесты

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build          # юнит-тесты + рандомизированная эквивалентность
./build/expassign_bench         # бенчмарк
./build/expassign_example       # пример использования
```

Тест `test_matchers_equivalence` — главная проверка корректности: 25 случайных
конфигураций × 800 случайных запросов, результаты наивного и индексного
матчеров сравниваются назначение-в-назначение, включая индексы секций (десятки
тысяч совпавших назначений за прогон). Уплощённые списки дополнительно
мутируются, чтобы покрыть OR-варианты, дыры между группами, секции и цепочки
слот-проверок. `test_config_loader` проверяет разбор продакшен-формата и
сквозной матчинг по нему.

## Пример

```cpp
#include "expassign/expassign.hpp"
using namespace expassign;

Config config;

DimensionConfig ui;                       // взаимоисключающие UI-эксперименты
ui.id = "ui-dimension";
ui.id_key = "uid";
ui.salt = "ui-2026";
ui.total_slots = 100;
ui.constraints = {std::make_shared<StringConstraint>(
    "service", std::vector<std::string>{"web"})};

ExperimentConfig header;
header.id = "new-header";
header.id_key = "uid";
header.salt = "hdr-1";
header.total_buckets = 100;
header.groups = {{"control", 50}, {"treatment", 50}};
for (uint32_t s = 0; s < 30; ++s) header.slots.push_back(s);  // 30% слотов
header.constraints = {
    VersionConstraint::Parse("app_version", "[2.0,3.0); [3.1.5,]"),
    std::make_shared<DomainConstraint>(
        "host", std::vector<std::string>{"*.example.{tld}"}),
};
ui.experiments.push_back(header);
config.dimensions.push_back(ui);

IndexedMatcher matcher(Flatten(config), std::make_shared<XXHash64Hasher>());

Request req;
req.strings["service"] = "web";
req.versions["app_version"] = *Version::Parse("2.7.1");
req.domains["host"] = "www.example.com";
req.ids["uid"] = "user-39";

for (const Assignment& a : matcher.Match(req)) {
  // a.ExperimentId(), a.GroupName()
}
```

## Структура

```
include/expassign/
  expassign.hpp            — единая точка подключения
  request.hpp, version.hpp — модель запроса и тип версии
  constraints/             — классы ограничений (по файлу на класс)
  region_tree.hpp          — дерево регионов и диапазоны IP
  experiment.hpp           — конфигурация экспериментов и измерений
  flatten.hpp              — плоская модель: варианты ограничений, цепочки
                             слотов, группы-диапазоны с секциями
  config_loader.hpp        — загрузка продакшен-формата JSON
  hash.hpp, bucketing.hpp  — реестр хеш-функций, слоты и бакеты
  bitset.hpp               — битсет для индексного матчера
  naive_matcher.hpp        — эталонный матчер
  indexed_matcher.hpp      — оптимизированный матчер
src/                       — реализации
tests/                     — юнит-тесты и тест эквивалентности
bench/, examples/          — бенчмарк и пример
```
