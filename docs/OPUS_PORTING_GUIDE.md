# Инструкция для Opus: перенос быстрого назначения экспериментов в существующую кодовую базу

Ты переносишь подход, реализованный в репозитории `allmycode/exps-maga`
(эталонная реализация — хороший источник деталей, но копировать код дословно
не нужно), в закрытый репозиторий, где **классы предметной области уже
существуют**. Твоя задача — встроить в них быстрый матчер экспериментов, а не
переписать их.

## 1. Цель

Есть список экспериментов (возможно, лежащих в «измерениях» — экспериментах
более высокого порядка). У каждого — набор ограничений на свойства запроса и
правило разбиения пользователей по хешу с солью. Нужно:

1. **Наивный матчер** — линейный обход экспериментов с проверкой каждого
   ограничения «в лоб». Он — эталон корректности, оптимизировать его нельзя.
2. **Индексный матчер** — инвертированные индексы по свойствам + плотные
   битовые множества. Целевая скорость: десятки тысяч экспериментов за
   заметно меньше 1 мс на запрос (в эталонной реализации 30 000 экспериментов
   матчатся за ~74 мкс).
3. **Рандомизированный тест эквивалентности** двух матчеров — главный
   критерий приёмки: результаты должны совпадать назначение-в-назначение.

## 2. Порядок работы (обязательный)

1. **Сначала инвентаризация.** Найди в репозитории существующие аналоги
   каждой роли из раздела 3 и выпиши соответствие «роль → существующий класс,
   файл, отличия от эталона». Не пиши ни строчки индекса, пока не ответишь на
   вопросы из раздела 4.
2. Если какой-то роли нет — создай минимальный адаптер/класс в стиле
   репозитория (именование, структура каталогов, система сборки, тестовый
   фреймворк — всё как принято там, а не как в эталоне).
3. Реализуй наивный матчер поверх существующих классов и покрой его юнит-
   тестами. Только после этого — индексный.
4. Индексный матчер добавляй по одному типу индекса (строки → булевы →
   версии → домены), после каждого прогоняя тест эквивалентности.
5. В конце — бенчмарк на синтетической конфигурации из тысяч экспериментов и
   фиксация цифр в описании изменений.

## 3. Роли и их семантика

Соответствие ищи по смыслу, названия в закрытом репозитории будут другими.

| Роль | Что делает |
|------|------------|
| **Запрос** | Именованные свойства четырёх типов: строки, булевы, версии (`1.2.3.4`, компонентов сколько угодно), домены (интернет-хост); плюс идентификаторы пользователя (несколько типов: uid, device_id, ...). |
| **Версия** | Сравнение с выравниванием нулями: `1.2 == 1.2.0`. |
| **Ограничение** | Привязано к одному свойству; проверяет запрос. **Отсутствующее в запросе свойство не удовлетворяет никакому ограничению на него** (в т.ч. негативному строковому — это частая ошибка). |
| **Строковое ограничение** | Набор строк + флаг «входит / не входит». |
| **Булевое ограничение** | Точное значение true/false. |
| **Ограничение по версии** | Набор интервалов, каждая граница включающая или исключающая, границы могут отсутствовать (±∞). Выполнено, если версия попала хотя бы в один интервал. |
| **Ограничение по домену** | Шаблоны вида `*.example.{tld}`: `*` — только самая левая метка, означает любое число дополнительных поддоменов; `{tld}` — только самая правая метка, любой один TLD. Сопоставление регистронезависимое, по меткам, не по подстрокам. **Зафиксируй и задокументируй семантику `*`**: в эталоне `*` покрывает и ноль поддоменов (`*.example.ru` матчит `example.ru`); если в закрытом репозитории уже принято иначе — сохрани их семантику, но одинаково в обоих матчерах. |
| **Дерево регионов** | Геобаза: регион — целое число, у каждого, кроме корневого, есть родитель. Плюс диапазоны IP → регион. Операции: цепочка предков региона (регион входит в заданный, если тот встретился в цепочке, включая сам регион) и «регион по IP». Неизвестный дереву регион — цепочка из него одного. |
| **Ограничение по регионам** | Набор регионов + флаг «входит / не входит». Регион запроса разрешается так: явный id из запроса; если его нет — по IP пользователя через дерево. Не удалось определить — ограничение не выполнено в обоих режимах. Явный id **приоритетнее** IP. |
| **Эксперимент** | id, ограничения (OR-список AND-групп — «вариантов»; пустой — без ограничений), тип идентификатора (`id_key`), алгоритм хеша + соль, число бакетов, группы. Группа (testid) занимает диапазон бакетов; диапазоны могут идти с дырами — бакет вне всех групп не даёт назначения. У группы могут быть секции: payload + собственные ограничения, проверяемые только для выигравшей группы. |
| **Измерение** | Свои ограничения, свой `id_key`, алгоритм+соль и `total_slots`; каждый эксперимент занимает набор слотов, слоты разных экспериментов одного измерения не пересекаются (валидируй). В общем виде у эксперимента **цепочка** слот-проверок (вложенные разбиения); в конфиге это все «места» (places), кроме последнего — последнее задаёт разбиение на группы. Измерение в конфиге неявное: места разных записей с одинаковой тройкой (id, соль, size) — одно измерение. |
| **Реестр хешеров** | Разбиения указывают алгоритм: соль вида "XXH3:abcd" — алгоритм до ':', соль после; без префикса — алгоритм по умолчанию. Неизвестный алгоритм — ошибка на этапе построения матчера, не в рантайме запроса. |
| **Уплощение** | Перенос ограничений и параметров слотов измерения внутрь каждого его эксперимента → плоский список. Оба матчера работают только с ним. |
| **Хешер** | Интерфейс с методом `uint64 Hash(string_view)`. Вход — конкатенация `значение_идентификатора + соль`. Если в репозитории уже есть XXH3/xxhash — используй его; не реализуй хеш сам без нужды (в эталоне рукописный XXH64 был проверен на векторах `XXH64("")==0xEF46DB3751D8E999`, `XXH64("abc")==0x44BC2CF5AD770999` — и тест сразу поймал опечатку в константе). |

Порядок проверки в обоих матчерах строго одинаков: ограничения (хотя бы один
вариант целиком) → цепочка слот-проверок (`hash(id+salt) % total_slots`
входит в слоты эксперимента, по каждой проверке) → бакет
(`hash(id+salt) % total_buckets` → группа по диапазонам, дыра — нет
назначения) → секции выигравшей группы. Отсутствие нужного идентификатора в
запросе — эксперимент не назначается.

## 4. Вопросы инвентаризации (ответь письменно до кодирования)

- Как в репозитории представлен запрос? Разделены ли пространства имён
  свойств по типам (строковое `host` и доменное `host` — разные свойства)?
- Есть ли уже базовый класс/концепт ограничения? Какая у него сигнатура
  проверки — по запросу целиком или по значению? (Индексу нужны **данные**
  ограничения: набор строк, интервалы, шаблоны — если они инкапсулированы,
  добавь const-геттеры, не ломая инкапсуляцию остального.)
- Есть ли измерения/слои и в каком виде? Есть ли уже уплощение?
- Какой хеш и как формируется вход (конкатенация? разделитель? порядок
  id/соль)? **Не меняй существующую формулу** — иначе пересоберутся все
  выборки пользователей.
- Может ли у эксперимента оказаться несколько ограничений на одно свойство
  (своё + от измерения)? (Почти наверняка да — это влечёт «слои», см. 5.3.)
- Есть ли уже геобаза/дерево регионов и резолвер IP → регион? Используй их
  как есть (обычно это готовый сервис или библиотека); индексу от них нужны
  только «цепочка предков» и «регион по IP».
- Однопоточное ли использование? Матчер после построения должен быть
  иммутабельным и безопасным для конкурентных `Match` (в эталоне все
  временные буферы — локальные переменные запроса).

## 5. Индексный матчер — точная спецификация

### 5.1. Битсет

Плотный битсет по числу экспериментов N (слова uint64). Нужны: `Set/Reset/
Test`, `SetAll` (с обнулением хвостовых битов за пределами N!), `&=`, `|=`,
копирование без реаллокации, `Any`, итерация по установленным битам через
count-trailing-zeros (`w &= w - 1` в цикле).

### 5.2. Общая схема

Ограничения эксперимента — OR-список AND-групп (вариантов). **Бит индекса —
вариант, не эксперимент**: варианты одного эксперимента лежат в битовом
пространстве подряд, эксперимент без ограничений получает один вариант без
ограничений. Для каждого свойства строится индекс, который по запросу отдаёт
битсет `out`: бит v установлен ⇔ ограничение варианта v на это свойство
выполнено. **Варианты без ограничения на свойство в битсете всегда
установлены** (битсет `unconstrained`, предвычисляется). Если свойства нет в
запросе — `out = unconstrained` (все ограниченные отпадают).

Запрос: `acc = все_единицы`; для каждого индекса `acc &= index.Filter(req)`;
ранний выход при пустом `acc`. Эксперимент — кандидат, если выжил хотя бы
один его вариант; биты обходятся по возрастанию, варианты лежат подряд,
поэтому дедупликация — «помнить последний эксперимент». Затем для каждого
кандидата — цепочка слот-проверок и выбор группы (раздел 5.8). Ограничения
секций в индекс не входят: они проверяются в лоб только для выигравшей
группы — тем же кодом, что и в наивном матчере.

### 5.3. Слои

Если у эксперимента два ограничения на одно свойство, в одном индексе они не
живут (бит один). Поэтому у свойства — список «слоёв»: при добавлении
ограничения оно кладётся в первый слой, где этого эксперимента ещё нет, иначе
создаётся новый слой. Каждый слой — самостоятельный индекс со своим
`unconstrained`; слои пересекаются через `acc` как независимые свойства.
Слоёв на практике 1–2, это дёшево.

### 5.4. Строковый индекс (слой)

Хранит: `unconstrained`; битсет `negated` (эксперименты с «не входит»);
`in_lists: value → список id` (позитивные, содержащие value);
`not_in_lists: value → список id` (негативные, содержащие value).

```
Filter(req):
  out = unconstrained
  если свойства нет в запросе → return
  out |= negated
  для id из not_in_lists[value]: out.Reset(id)   // сначала сбросы
  для id из in_lists[value]:     out.Set(id)     // потом установки
```
Порядок безопасен, т.к. внутри слоя эксперимент либо позитивный, либо
негативный. Списки — разреженные (vector<uint32>), не битсеты: экономия
памяти при тысячах значений.

### 5.5. Индекс версий (слой)

Собери все границы интервалов слоя, отсортируй, убери дубли → `points`.
Ось версий делится на `2*|points|+1` регионов: чётный регион `2i` — открытый
промежуток перед `points[i]`, нечётный `2i+1` — сама точка `points[i]`.
На каждый регион — битсет (сразу инициализированный `unconstrained`).
Для интервала эксперимента e:

```
first = 0, если lo нет; иначе i = индекс lo в points,
        first = (lo включающая ? 2i+1 : 2i+2)
last  = 2*|points|, если hi нет; иначе j = индекс hi в points,
        last = (hi включающая ? 2j+1 : 2j)
для r in [first, min(last, максимальный регион)]: regions[r].Set(e)
```
Пустые интервалы (first > last) корректно не помечают ничего. На запрос:
бинарный поиск версии в `points` (нашлась точно → регион `2i+1`, иначе `2i`
по точке вставки), `out = regions[r]`. Сравнение версий — то же выровненное
нулями, что и в наивном матчере, иначе эквивалентность сломается на
`2.0` vs `2.0.0`.

Память: `регионы × N/8` байт на слой. При большом числе уникальных границ
это может распухнуть — если в закрытом репозитории границ реально тысячи,
замени битсеты регионов на разреженные списки + сортированную развёртку, но
сперва померь: обычно уникальных границ десятки.

### 5.6. Доменный индекс (слой)

Префиксное дерево по меткам хоста **от TLD к младшим** (метки в нижнем
регистре). Узел: `children: метка → узел`, отдельное ребро `tld_child`
(шаблоны с `{tld}`), списки `star_exps` (шаблоны с `*`, чей фиксированный
суффикс кончается в этом узле) и `exact_exps` (шаблоны без `*`).

Вставка шаблона: от корня — сначала `tld_child`, если `{tld}`, затем
фиксированные метки; эксперимент — в `star_exps` или `exact_exps` конечного
узла.

Обход на запрос: хост нормализуй так же, как в наивном матчере (нижний
регистр, одна завершающая точка FQDN срезается, пустая метка → хост
невалиден, ничего не матчится). Идём по меткам от TLD; из корня возможны две
ветки (точная метка и `tld_child`), дальше только точные — активных узлов
всегда ≤ 2. **На каждом посещённом узле** добавляй в `out` его `star_exps`
(семантика «ноль и более поддоменов»); `exact_exps` — только когда потреблены
все метки хоста.

### 5.7. Индекс регионов (слой)

Хранит: `unconstrained`, битсет `negated`, `in_lists: регион → эксперименты`
и `not_in_lists: регион → эксперименты` (как у строк, но ключ — id региона).
Предвычислять транзитивные замыкания дерева не нужно:

```
Filter(req):
  out = unconstrained
  регион = явный id из запроса, иначе регион по IP; нет → return
  out |= negated
  для каждого предка a региона (включая сам регион):
    для e из not_in_lists[a]: out.Reset(e)
    для e из in_lists[a]:     out.Set(e)
```
Глубина дерева — единицы, поэтому это O(depth) map-lookup'ов. Порядок
Set/Reset между предками безопасен: внутри слоя эксперимент либо позитивный,
либо негативный. Все ограничения слоя обязаны разделять один экземпляр
дерева — проверь при построении и бросай ошибку конфигурации.

### 5.8. Слоты, бакеты и кеш хешей

После пересечения битсетов для каждого кандидата:
1. по каждой слот-проверке цепочки: хеш по (id_key, алгоритм, соль) → слот;
   бинарный поиск по отсортированным слотам эксперимента;
2. хеш финального разбиения → бакет → группа бинарным поиском по диапазонам
   `[begin, end)` (диапазоны отсортированы, могут идти с дырами); бакет вне
   всех групп → нет назначения;
3. для выигравшей группы — индексы секций, чьи ограничения выполнены.

Эксперименты одного измерения используют одну тройку (id_key, алгоритм,
соль) — при построении интернируй уникальные тройки в таблицу (заодно
проверяя, что алгоритм зарегистрирован), на запрос заведи локальный кеш
«индекс тройки → {не вычислено | id отсутствует | хеш}». Это срезает сотни
вычислений хеша до единиц.

## 6. Тесты

1. **Юнит-тесты** каждого типа ограничения на существующих классах, включая
   краевые случаи: отсутствующее свойство (позитив и негатив), исключающие
   границы (`[1.0,2.0)` и запрос `2.0`, `2.0.0`), `1.2 == 1.2.0`, регистр и
   FQDN-точка в доменах, хост из одной метки, holdout-бакеты, пустой матчер;
   для регионов: вложенность через несколько уровней, регион == заданному,
   неизвестный дереву id (негативное ограничение при этом матчится!),
   разрешение по IP, приоритет явного id над IP, IP вне диапазонов и
   некорректный IP.
2. **Рандомизированная эквивалентность** (главный тест): генератор случайных
   конфигураций (несколько измерений со случайными непересекающимися
   слотами + свободные эксперименты; 0–3 ограничения на эксперимент и на
   измерение, все пять типов, негативные строковые/региональные ~50%, границы
   интервалов иногда отсутствуют; случайное дерево регионов на ~30 узлов, в
   ограничениях иногда неизвестные дереву id) и случайных запросов (каждое
   свойство присутствует с вероятностью ~0.75, идентификаторы ~0.9; регион то
   явным id, то через IP — в том числе IP вне диапазонов и мусорные строки). Пулы значений делай маленькими,
   чтобы ограничения часто срабатывали. Десятки сидов × сотни запросов;
   сравнивай списки назначений поэлементно (id эксперимента + индекс группы,
   порядок — порядок плоского списка в обоих матчерах). **Обязательно
   assert'ни, что суммарно назначений много** (тысячи) — иначе тест может
   молча сравнивать пустоту.
3. **Бенчмарк**: 10k–30k синтетических экспериментов, 2–5 ограничений на
   каждый; замеряй avg/p50/p99 на запрос отдельно для наивного и индексного.
   Ориентир эталона: 10k → ~30 мкс, 30k → ~75 мкс (Release, -O2).

## 7. Подводные камни (каждый из них реально стрелял)

- Хвостовые биты `SetAll` за пределами N: не очистишь — получишь «фантомные»
  эксперименты при итерации.
- `unconstrained` считается **на слой**, а не на свойство.
- Негативное строковое ограничение при отсутствующем свойстве — НЕ матч.
- В формуле региона для исключающей нижней границы — `2i+2` (легко написать
  `2i+1` и потерять точку).
- Семантика `*` (ноль или ≥1 поддоменов) должна быть одинакова в наивном
  матчере, индексе и задокументирована.
- Разрешение региона (явный id → IP → «не определён») — общая функция для
  обоих матчеров, иначе они разойдутся на приоритете id над IP.
- Неизвестный дереву регион ≠ «регион не определён»: он определён и входит
  только сам в себя, поэтому негативное ограничение на нём матчится, а при
  неопределённом регионе — нет.
- OR-варианты: пустой список вариантов — «без ограничений», но вариант с
  пустым AND-списком внутри непустого списка тоже матчит всё — нормализуй
  при загрузке конфига (пустой блок поглощает остальные).
- Если генератор эквивалентности строит конфиги через программный API,
  который даёт только один вариант и последовательные группы, — мутируй
  уплощённый список (разрезай AND на OR-варианты, делай дыры между группами,
  добавляй секции и уровни слот-проверок), иначе новые ветки кода не
  покрываются.
- Разбиение (слоты/бакеты/хеш) в двух матчерах должно быть одним и тем же
  кодом или тестироваться отдельно — эквивалентность ловит расхождения только
  там, где пути различаются.
- Не меняй существующие формулы хеширования/солей — это молча пересоберёт
  выборки живых экспериментов.
- Матчер после построения — только чтение; никаких mutable-кешей между
  запросами без синхронизации.

## 8. Критерии приёмки

- [ ] Существующие классы переиспользованы; новые файлы следуют стилю и
      структуре закрытого репозитория.
- [ ] Наивный и индексный матчеры реализуют один интерфейс.
- [ ] Тест эквивалентности зелёный и реально назначает (счётчик назначений
      в assert'е).
- [ ] Бенчмарк: ≥10k экспериментов, индексный < 1 мс на запрос с запасом.
- [ ] Валидация конфигурации: пересечение слотов, слот ≥ total_slots,
      переполнение бакетов, пустые id — внятные ошибки.
- [ ] Вся существующая функциональность репозитория не затронута (полный
      прогон их тестов).
